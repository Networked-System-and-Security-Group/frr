## 2. 锚点清理修复

`midr_stop_rep_probe_entry()` 在清理代表候选前检查 Session 台账。已登记为 `CL_ANCHOR` 的代表保留 PM 探测、Link 记录和 GRE；未选中的候选仍按原流程清理。回归测试覆盖选中代表保留、未选候选清理以及既有虚链路生命周期。

实际观察中，WLQ 到北航的 `CL_ANCHOR` 会话、PM Link 和 GRE 在锚点评估结束后持续保留。昆明也保留了到北航和 WLQ 的两个锚点。该结果验证了选中锚点不再被代表候选清理误删除。

`PM up` 统计 `show midr links` 中的测量状态，包含候选和锚点，不等同于 TED 的有效拓扑边数。GRE `READY` 表示本端接口创建完成；`overlay reachable` 才表示本端 overlay 探测成功。表格是一轮采集快照，路由波动需结合各节点的连续观察记录判断。

边缘节点的 Prefix Provider 把本地 BGP RIB 中的前缀作为本节点发布的 Prefix 输入 MIDR。因此 SPF `local` 不表示所有前缀都直接连接在本机，也不能据此证明 MIDR 跨群选路或业务转发完成。

## 5. 数据面与路由观察

在武汉 R1 属于群 2 的上线观察阶段，复旦到武汉 R1 的同群 overlay Ping 为 3 发 3 收、零丢包，RTT 约 16 ms。对应 GRE 两端均可看到同群会话和 overlay 探测，证明该同群隧道可转发。

跨群方向仍存在回配端未创建反向 GRE 的问题。例如 WLQ 侧到北航的 Session 为 `CL_ANCHOR / Established`，PM 为 up，GRE 为 `READY / overlay unreachable`；北航侧对应会话为 `PEER_REQ_REPLY / Established`，但没有到 WLQ 的 PM Link 或 GRE。代码中公共建连路径仅为 `CL_ANCHOR` 额外启动 PM，跨群 `PEER_REQ_REPLY` 没有相同动作。锚点保留修复不等于该双向建链问题已经解决。

武汉 R2 在加入阶段曾进入群 2，但观察到 transport 路由被 MIDR 业务汇总路由覆盖。一次记录中，9 条 `proto 199` 前缀经复旦 GRE 安装后，到 `240a:a00f:100:1::2` 和 `240a:a00f:800:1::2` 的查询也指向 `mgre-65000000`。同一时间会话的 Up/Drop 计数反复增加。GRE 外层端点需要继续走 underlay；业务汇总路由覆盖端点会形成递归依赖，因此仅保留默认网关不足以保证控制面持续可达。

结论：锚点误清理修复已通过回归和实网保留观察，代表调整已部署，同群 GRE 已有成功实例。跨群反向 GRE 和 transport 路由隔离仍未完成，整网跨群业务验收不能判定为通过。
