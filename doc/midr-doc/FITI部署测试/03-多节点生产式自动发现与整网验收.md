# 03 多节点生产式自动发现与整网验收

本文用于在 FITI 真实三层 underlay 上验证 MIDR 多节点生产式流程：bootstrap 骨干、普通节点自动发现、自动分群、Session 建立、Node/Link 状态传播、TED/SPF、Zebra/FIB、GRE 虚链路和业务流量。本实验采用固定节点角色：少量边缘 MIDR 节点运行发布包中的 FRR 10.7.0-dev `bgpd`，与本站 BGP-R 交换外部路由；外部 BGP-R 保持现有 FRR 8.4.4；内部 MIDR 和专职 bootstrap 只运行 `midrd + zebra`，通过本站 BGP-R 的默认网关访问 underlay。两种 FRR 版本只在不同主机间通过 BGP-4 互操作，不在同一主机混用 `libfrr` 或 Zebra。所有阶段使用同一角色表和同一配置模型，不在测试过程中切换架构。

本文与 00-公共前置与版本部署.md 配套。00 文档负责发布包、共享库、进程生命周期、持久目录和通用排障；本文负责 12 台 MIDR 路由器的多节点部署和整网验收。01、02 是两节点 Session/GRE 冒烟实验，不是本文的前置条件。

实际部署不逐台手工执行。分阶段编排脚本、12 节点清单和阶段门禁见 [FITI 12 节点部署编排](../../midr-test/fiti-deploy/README.md)。本文件给出每个阶段的协议配置和验收判据，编排 README 给出批量执行顺序；阶段 0 的只读盘点脚本完成前，不执行批量部署。

## 当前实现基线

本轮发布包包含 Prefix Provider。边缘 MIDR 的 Provider 读取本站匹配版本 `bgpd` 的有效 BGP RIB，通过 `/run/midr/prefix.sock` 发送 `SNAPSHOT_BEGIN`、`UPSERT`、`SNAPSHOT_END`、`EOR` 以及后续 `WITHDRAW`；内部 MIDR 不运行 `bgpd`，只接收 MIDR Prefix 和 Link 状态。

固定角色为：bootstrap `108/111`，Group 1 初始代表 `102`（北航），Group 2 初始代表 `101`（复旦）；`107/110` 是内部普通成员，其余 6 台是边缘普通成员。共有 2 台专职 bootstrap、2 台内部业务节点和 8 台边缘业务节点。普通成员不预配置群号，实际群组由自动加入流程决定，不限定全网只有群 1、2。第 12 节点 `TEIN-MIDR_pku` 使用 `240a:a00f:f000:737::f037`，通过 `240a:a00f:f000:737::f007` 接入 TEIN-B1。

代码已经包含 `INTER_GROUP` SPF 路由范围和 Zebra/FIB 安装路径。跨群验收需要两端 Session、持续的链路探测、双向可达 GRE、有效 Link 事实和 SPF 下一跳共同成立。`CL_ANCHOR` 或 `PEER_REQ_REPLY` 为 Established 只证明控制会话建立；GRE 为 READY 只证明本端接口已创建，还必须检查 `overlay reachable`。缺少双向 GRE 或有效下一跳时，应沿建连、探测和 Link 上报路径排查，调整管理距离不能补齐这些条件。

## 一、实验范围和角色

### 1.1 FITI 的节点职责

2026-09-30 环境说明和三份 L3 文档中的节点职责如下：

| 节点类别 | FITI 节点 | 当前 underlay 进程 | 本实验职责 |
|---|---|---|---|
| 业务终端 | Terminal_fudan、Terminal_buaa、Terminal_wlq、Terminal_kmn、Terminal_qda | 无 FRR 控制面进程 | 产生和接收业务数据包 |
| eBGP 边界路由器 | BGP-R_sh、BGP-R_fudan、BGP-R_buaa、BGP-R_wlq、BGP-R_kmn、BGP-R_qda、BGP-R_wh、BGP-R_zhz | `zebra`、`bgpd` | eBGP/站点路由、发布 MIDR transport 可达性、转发 underlay 报文 |
| TEIN 边界路由器 | TEIN-B1_pku、TEIN-B2_pku | `zebra`、`bgpd`、`ospf6d` | eBGP 接入和 TEIN OSPFv3 骨干边界转发 |
| TEIN 内部路由器 | P_pku | `zebra`、`ospf6d` | OSPFv3 underlay 骨干和跨区域 IP 转发 |
| MIDR 边缘路由器 | MIDR_fudan、MIDR_buaa、MIDR_wlq、MIDR_kmn、MIDR_qda、MIDR-R1_wh、MIDR-R1_zhz、TEIN-MIDR_pku | `zebra`、`bgpd`、`midrd`、Prefix Provider | 运行 MIDR 控制面，同时负责本站外部前缀的受控交换 |
| MIDR 内部路由器 | MIDR-R2_wh、MIDR-R2_zhz | `zebra`、`midrd`；不运行 `bgpd` 或 Provider | 参与 MIDR 自动发现、分群、Link、SPF、GRE 和 MIDR FIB |
| MIDR 专职引导节点 | MIDR-R3_wh、MIDR-R3_zhz | `zebra`、`midrd`；不运行 `bgpd` 或 Provider | 提供 bootstrap 目录服务，群号 0，不承担业务 GRE/FIB |

本实验的最终对象是 12 台 MIDR 路由器。BGP-R、TEIN-B1/B2 和 P 是 underlay 基础设施，不是额外添加的 MIDR 节点。它们通过已有 BGP/OSPFv3 路由转发 MIDR transport-address 之间的普通 IPv6 报文。普通站点的 MIDR 与本站 BGP-R 连接，TEIN-MIDR_pku 与 TEIN-B1 连接；接入路由器是本站 MIDR 的默认网关。边缘 MIDR 保留与本站 BGP-R 的 BGP Session；内部 MIDR 和专职 bootstrap 不运行 `bgpd`，使用本站网关提供的默认路由。`midrd` 不会自动启动、替换或配置 `bgpd` 和 `ospf6d`。

Underlay 链路表中的 1～15 号链路是跨站 eBGP 链路，16～18 号链路是 TEIN 内部 IGP/OSPFv3 链路；各站点内部的 BGP-R↔MIDR 和主机接入链路按 L3 地址规划和接口映射配置。MIDR 的 BGP Session 只存在于角色表指定的边缘 MIDR 与本站 BGP-R 之间，不把 MIDR overlay 虚链路当作 underlay 链路。

### 1.2 underlay 与 MIDR overlay 的关系

Fudan 的 MIDR transport-address 是 240a:a00f:100:1::2，Buaa、乌鲁木齐、昆明和青岛分别使用 200:1::2、300:1::2、400:1::2 和 500:1::2。云 A、云 B 的三个 MIDR 路由器分别使用 800:1::2～800:3::2 和 810:1::2～810:3::2。

这些地址不要求两台 MIDR 路由器物理直连。建立第一条 Session 前，必须确认本机 Linux 网络栈已经有到 bootstrap transport-address 的 IP 可达路径：

~~~bash
ip -6 route get <对端transport-address>
ping -6 -c 3 <对端transport-address> || true
~~~

如果 route get 显示经由 BGP-R、T1 或 TEIN 内部路由器转发，仍然属于正常的多跳 underlay。这个路径可以来自直连路由、静态路由、默认路由或外部 BGP/OSPFv3；静态路由不是 MIDR 的必选配置。underlay 路由器只转发 TCP、GRE 和业务报文，不参加 MIDR Session、群组和 SPF。

部分站点可能过滤 ICMP。`ping -6` 仅作为辅助检查；它失败时，仍应以 SSH、`ip -6 route get`、TCP 5871、Session 状态和日志为准。不能因为单次 ICMP 丢包就判定 transport 或 MIDR 节点不可用。

MIDR 的第一跳固定定义为本站 BGP-R。内部 MIDR 只需要在本地链路上可达本站 BGP-R，并在 Linux 路由表中存在默认路由或等效的 transport 汇总路由；它不通过 BGP 学习远端 transport 路由。边缘 MIDR 的 BGP 只用于既定的边界路由交换，不改变 MIDR 首跳仍经本站 BGP-R 的事实。默认路由由 netplan、DHCP、IPv6 RA 或其他网络管理系统持久化安装，不能根据“物理上连接了网关”这一事实自动推断。本站 BGP-R 和上游 underlay 必须能够双向到达所有可能的 MIDR transport-address。

正式部署在 `midrd.service` 的 `ExecStartPre` 中建立 transport 专用 IPv6 表 1990。本机 locator 发出的 TCP 5859/5871、UDP 控制和探测、GRE 外层报文使用该表的本站网关；业务流量继续使用 main 表。这样，即使 MIDR 学到的业务汇总前缀覆盖 transport-address，也不会把协议报文和 GRE 外层报文递归送入业务隧道。规则由本机 locator、网关和接口生成，不依赖全网邻居清单；配置和检查命令见 00 文档 3.2 节。

MIDR 的自动发现从 bootstrap 开始，但 bootstrap 不是 IP 转发代理。节点收到代表和成员的 transport-address 后，会直接对这些地址发起 TCP Session；当前代码没有把 MIDR Link 图转换成 Linux transport 路由，也没有通过 bootstrap 中继 Session。因此，仅有“到 bootstrap 的一条静态路由”只有在所有后续 transport-address 也能经同一条路由到达时才足够。若不同节点需要不同出口，必须由 underlay 提供相应路由。

这与 OSPF 的首跳机制不同。OSPF 在本地接口上发送链路本地 Hello/组播报文，不需要预先知道远端 Router-ID 的单播地址；形成邻接后再交换 LSA。当前 MIDR 实现的首跳是 `midr bootstrap <locator>` 发起 TCP `REP_LIST_REQ`，后续根据代表/成员列表中的 locator 直接建立 TCP Session。节点目录也只向已建立的 overlay 邻居发送，不能承担首跳发现。因此，当前部署可以不运行 `bgpd`，但仍需要经本站 BGP-R 的 connected route、静态/默认路由或其他外部 underlay，使首个 bootstrap 和随后选中的候选 locator 可达。真正的 OSPF 式接口组播发现、link-local transport 和不依赖 bootstrap locator 的首跳机制不属于当前 FITI 部署接口。

## 三、Prefix 输入方式

### 3.1 生产式输入

边缘节点使用 `MIDR_PREFIX_MODE=socket`，由 `midrd` 创建 `/run/midr/prefix.sock` 监听 socket；随后启动的 `midr-bgp-prefix-provider.service` 作为客户端连接它。Provider 读取本站 `bgpd` 的有效 BGP RIB，发送 snapshot、upsert、withdraw 和 EOR。当前 Provider 不扫描任意本地接口或 VRF；本地业务前缀需先按站点 BGP 策略进入本机 BGP RIB，或由另一个实现 Prefix IPC 的 Provider 提供。

内部节点和专职 bootstrap 使用 `MIDR_PREFIX_MODE=none`，不启动本地 Provider；内部节点从 MIDR 网络学习远端前缀，bootstrap 提供控制面目录服务。

服务顺序为 Zebra → 边缘 bgpd → midrd → 加载 node.commands → 边缘 Provider。在边缘节点上检查：

~~~bash
systemctl is-active midr-zebra midr-bgpd midrd midr-bgp-prefix-provider
test -S /run/midr/prefix.sock
NEW_DIR=$(readlink -f /opt/midr-current)
tail -n 30 /var/log/midr/*-prefix-provider.log
~~~

静态 `--prefix` 输入与 `--prefix-socket` 互斥。正式 systemd 参数由 `/etc/midr/node.env` 的 `MIDR_PREFIX_MODE` 决定，不手工追加两种输入。业务流量验收使用真实前缀；涉及 transport-address 的路由需同时核对 underlay 出口，避免把 MIDR 业务路径误用于 GRE 外层到自身节点的递归寻路。

### 3.2 业务 Prefix 要求

每个参与业务转发的 MIDR 节点应有唯一 Prefix，并且该 Prefix 不应同时被 underlay BGP 以更优路径直接发布。验收时必须能将业务流量归因于 MIDR 路由：

~~~bash
ip -6 route show proto 199
ip -6 route get <远端业务地址> from <本地业务地址>
ping -6 -c 3 -I <本地业务地址> <远端业务地址>
~~~

### 4.3 普通节点

自动分群测试中，普通节点不配置 group-id、midr session、--peer、--link：

~~~text

midr bootstrap <bootstrap-1-locator> remote-as <bootstrap-1-as> router-id <bootstrap-1-router-id>
midr bootstrap <bootstrap-2-locator> remote-as <bootstrap-2-as> router-id <bootstrap-2-router-id>

~~~

加载配置文件：

~~~bash

test -r "$NEW_DIR/midrd-vty.py"

~~~

正式启动时，`midrd.service` 的 `ExecStartPost` 会自动执行同样的加载动作；上面的命令仅用于恢复配置或排障。`node.commands` 是持久配置；`/run/midr/midrd.vty` 是运行时 socket，不能把 socket 当作配置备份。

### 4.4 新增群组

群 1、2 是初始预置群，不限制普通节点的实际群组。普通节点按代表目录、链路测量和加入策略选择群组；找不到可用群或满足 CREATE 条件时，可以自动创建新群并自任代表。验收记录实际群号和建群过程，不把全网只有两个群作为通过条件。额外预置群代表时，不需要为所有普通节点新增固定 Session。

代表身份属于其所在群。节点退出或切换群时清除旧代表身份；加入已有群不继承旧群的代表身份。同群的代表重入流程保留其身份，自动创建新群时可重新成为该新群代表。因此取消固定代表配置不会禁止普通节点为自己创建的新群担任代表。

例如新增群 3：

1. 选择一台未担任 bootstrap、具有稳定 underlay 和唯一 node-id 的节点作为群 3 代表。
2. 为该节点持久化配置：

~~~text
midr transport-address <新代表locator>
midr group-id 3
midr role group-rep
midr bootstrap <bootstrap-1-locator> remote-as <bootstrap-1-as> router-id <bootstrap-1-router-id>
midr bootstrap <bootstrap-2-locator> remote-as <bootstrap-2-as> router-id <bootstrap-2-router-id>
~~~

3. 启动或重载该节点，确认它的 Node fact 带有 group-id 3 和 `GROUP_REP` 能力；引导节点随后会把它纳入群代表目录。
4. 新上线的普通节点仍只配置 bootstrap 候选，不配置 group-id。它会根据代表目录和链路测量选择可用群组，群 3 也会成为候选。
5. 对已经稳定加入群 1 或群 2 的节点，不应期待它们因为新群出现而自动全部迁移；如需迁移，应通过持久配置和重启/重新加入流程明确执行，并重新验收 Node、Link、SPF 和 Prefix。

当前代码还支持在加入流程找不到可用群代表或群内成员不足时执行 `CREATE`，按现有最大群号加一创建新群，并允许首个节点自任代表。自动 CREATE 和加入既有群均属于普通节点的允许结果；代表选举和稳定态自动重平衡的具体行为按代码和集中采集结果核验，不以地理距离直接推断群号。

## 五、启动顺序

### 5.1 先确认 underlay FRR 进程和邻居

在本实验中，`midrd` 建立在已经运行的 underlay 之上。`midrd` 不负责启动 `bgpd` 或 `ospf6d`。边缘 MIDR 的 `bgpd` 只检查与本站 BGP-R 的既定 Session；内部 MIDR 不运行 `bgpd`。BGP-R、TEIN-B1、P 和 TEIN-B2 上的 underlay 邻居必须先达到预期；TEIN-MIDR_pku 作为第 12 台 MIDR，随后单独验证经 TEIN-B1 的默认路由。

FITI 当前设计使用 IPv6 OSPF，进程名是 `ospf6d`，不是 `ospfd`。`ospfd` 只有在另行部署 IPv4 OSPF 时才会出现，本实验不把它作为预期进程。

在每个 BGP-R、TEIN-B1/B2 和 P 上执行：

~~~bash
systemctl is-active frr || true
pgrep -a zebra || true
pgrep -a bgpd || true
pgrep -a ospf6d || true
pgrep -a ospfd || true
vtysh -d bgpd -c 'show bgp summary'
vtysh -d bgpd -c 'show bgp ipv6 unicast summary'
~~~

`show bgp summary` 中，预期邻居状态为 `Established`；邻居数量应与 `l3-addressing-plan.md`、PPT 第 5 页和现场配置一致。`ospfd` 没有输出不代表故障，IPv6 underlay 应检查 `ospf6d`。

在边缘 MIDR 上额外执行：

~~~bash
pgrep -a bgpd
vtysh -d bgpd -c 'show bgp summary'
~~~

预期边缘 MIDR 仅保留角色表规定的本站 BGP-R 邻居。在内部 MIDR 上执行：

~~~bash
if pgrep -x bgpd >/dev/null; then
  echo 'unexpected bgpd on internal MIDR' >&2
  exit 1
fi
~~~

在 TEIN-B1、TEIN-B2 和 P 上执行：

~~~bash
pgrep -a ospf6d || true
vtysh -d ospf6d -c 'show ipv6 ospf6 neighbor'
vtysh -d ospf6d -c 'show ipv6 ospf6 route'
~~~

预期 OSPFv3 邻居状态为 `Full`。如果节点没有配置 OSPFv3 邻居，应根据拓扑表确认它是否属于 OSPFv3 四节点骨干，而不是把所有 FITI 节点都强行要求运行 `ospf6d`。

记录一份 underlay 进程和邻居证据：

~~~bash
{
  date -u
  hostname
  printf '%s\n' '--- processes ---'
  pgrep -af 'zebra|bgpd|ospf6d|ospfd' || true
  printf '%s\n' '--- bgp ---'
  vtysh -d bgpd -c 'show bgp summary' 2>&1 || true
  printf '%s\n' '--- ospf6 ---'
  vtysh -d ospf6d -c 'show ipv6 ospf6 neighbor' 2>&1 || true
} > /var/log/midr/<node-name>-underlay-check.txt
~~~

只有 underlay 的 BGP/OSPFv3 邻居达到预期、边缘/内部角色进程符合角色表、且每台本站 BGP-R 已经具备所有 transport 前缀的双向路径后，才进入 MIDR transport-address 和 Session 检查。

在 90 上先执行只读盘点和 transport 路由矩阵检查：

~~~bash
cd /home/guest/yhy/frr
~~~

`collect-underlay.sh` 只检查节点能否访问和现有服务状态；`check-transport-matrix.sh` 从每台 MIDR 对每个清单中的 transport-address 执行 `ip -6 route get`。只要任一节点出现 `Network is unreachable`，就停在 underlay 阶段，不启动或重启 MIDR。

矩阵通过后，使用批量脚本为所有 MIDR 写入本站 BGP-R 默认网关：

~~~bash
bash midr-test/fiti-deploy/install-midr-default-gateways.sh \
  --inventory midr-test/fiti-deploy/inventory-12.csv \
  --dry-run

  --inventory midr-test/fiti-deploy/inventory-12.csv \
  --apply
~~~

脚本按 transport-address 自动生成 `::1` 网关，备份 `60-ens4.yaml` 和 `61-l3.yaml`，验证带外文件不变，生成 Netplan 配置并立即安装默认路由。它不启动、停止或重启 FRR。执行后必须重新运行路由矩阵并得到 `checked=12 failed=0`。

在每台 MIDR 路由器上确认本机地址和到 bootstrap 的路径：

~~~bash
ip -6 addr show
ip -6 route show default
ip -6 route get <bootstrap-1-locator>
ip -6 route get <bootstrap-2-locator>
ping -6 -c 3 <bootstrap-1-locator> || true
ping -6 -c 3 <bootstrap-2-locator> || true
~~~

主验收中，`ip -6 route show default` 应显示经本站 BGP-R 的默认路由，或者显示覆盖全部 transport-address 的等效汇总路由；`ip -6 route get` 的下一跳应为本站 BGP-R 或该网关提供的等效路径。Linux 不会根据物理连接自动选择默认网关，默认路由必须由 netplan、DHCP、RA 或其他网络管理系统持久化配置。每台 MIDR 的本站网关地址按 `l3-interface-mapping.md` 的站点链路表填写，例如 Fudan 为 `240a:a00f:100:1::1`，Buaa 为 `240a:a00f:200:1::1`；云 A 的 R1/R2/R3 分别使用 `240a:a00f:800:1::1`、`:800:2::1`、`:800:3::1`，云 B 对应 `240a:a00f:810:1::1`、`:810:2::1`、`:810:3::1`。

在持久化 netplan 之前，先只对一台内部 MIDR 做临时默认路由试验。例如云 A 的 R2：

~~~bash
ssh -p 13007 root@118.229.43.234
ip -6 route replace default via 240a:a00f:800:2::1 dev ens5
ip -6 route show default
ip -6 route get 240a:a00f:100:1::2
ping -6 -c 3 240a:a00f:100:1::2
~~~

临时试验只修改当前内核路由，重启后不会保留；回滚命令为：

~~~bash
ip -6 route del default via 240a:a00f:800:2::1 dev ens5
~~~

只有该试验确认本站 BGP-R 能转发远端 transport-address 后，才把默认路由写入 `/etc/netplan/61-l3.yaml` 并执行 `netplan try`；不要在 12 台节点上直接批量执行 `netplan apply`。

本轮 R2 试验的持久化命令如下。该命令只备份和修改 `61-l3.yaml`，不会修改 `60-ens4.yaml`：

~~~bash
cp -a /etc/netplan/61-l3.yaml \
  "/root/61-l3.yaml.before-default-$(date -u +%Y%m%dT%H%M%SZ)"
cp -a /etc/netplan/60-ens4.yaml \
  /root/60-ens4.yaml.before-midr-gateway

python3 - <<'PY'
from pathlib import Path

path = Path('/etc/netplan/61-l3.yaml')
text = path.read_text()
gateway = '240a:a00f:800:2::1'
route = (
    '      routes:\n'
    '        - to: "::/0"\n'
    f'          via: "{gateway}"\n'
    '          metric: 1024\n'
)
if '      routes:' in text:
    raise SystemExit('61-l3.yaml already contains ens5 routes; inspect manually')
marker = '    ens4:\n'
if marker not in text:
    raise SystemExit('cannot find ens4 boundary in 61-l3.yaml')
text = text.replace(marker, route + marker, 1)
path.write_text(text)
PY

netplan generate
netplan try --timeout 120
~~~

`netplan try` 应在当前 SSH 会话中等待确认；确认新的地址、SSH 和路由都正常后按提示确认。若不确认，Netplan 会在超时后回滚；该命令的设计目的就是避免远程修改网络配置后失去管理连接。[Netplan `netplan try`](https://netplan.readthedocs.io/en/stable/netplan-try/)

确认后检查：

~~~bash
cmp /etc/netplan/60-ens4.yaml /root/60-ens4.yaml.before-midr-gateway
ip -6 route show default
ip -6 route get 240a:a00f:100:1::2 from 240a:a00f:800:2::2
ip -6 route get 240a:a00f:810:3::2 from 240a:a00f:800:2::2
~~~

到 R3 仍显示 `proto bgp` 并不矛盾：当前本机 `bgpd` 尚未停止，具体 BGP 路由优先于默认路由。后续内部 MIDR 单节点试点时，保存 BGP 状态后停止该节点 `bgpd`，再重复两个 `route get`，用于验证这些地址在没有本机 BGP 的情况下仍能经本站 BGP-R 到达。

失败时先修复直连路由、静态路由、默认路由、BGP/OSPFv3、转发和防火墙，不进入 MIDR 排障。

静态路由的选择按部署形态决定：

| 部署形态 | MIDR 节点需要的 underlay 路由 |
|---|---|
| 所有 transport-address 位于同一二层或同一前缀 | 内核自动生成的 connected route 即可 |
| 每个 MIDR 节点只有一个本站 BGP-R/underlay 网关 | 一条到 transport 地址汇总前缀的静态路由或默认路由可能足够，前提是该网关能转发所有已发现节点 |
| 多个站点、多个出口或不同路径 | 需要对应的静态汇总/明细或外部 BGP/OSPFv3 路由 |
| 希望 MIDR 自己为 transport-address 安装底层路由 | 当前代码未实现，不能把 overlay SPF 当作 transport underlay 路由协议 |

所有 12 台 MIDR 路由器由 `midrd.service` 使用 `/etc/midr/node.env` 启动。启动参数由服务脚本从持久配置生成：`--node-id`、`--listen`、`--zserv-path`、`--vty_socket`、`--sequence-file` 和 PID 文件使用节点变量；边缘节点的 `MIDR_PREFIX_MODE=socket` 会加入 `--prefix-socket` 并由 midrd 创建监听 socket；内部节点和专职 bootstrap 为 `none`。

### 5.6 分阶段上线

严格按以下顺序启动：

1. 依次启动 `MIDR-R3_wh`、`MIDR-R3_zhz`，加载 bootstrap 配置，等待骨干 Session 建立。
2. 依次启动 `MIDR_buaa`、`MIDR_fudan`，加载固定 group-id、group-rep 和 bootstrap 候选。
3. 先启动一个普通节点，只加载 bootstrap 候选，观察自动发现和入群。
4. 其余普通节点逐台上线。每台节点至少等待一次完整的 REP、MEMBER、Session 和 EOR 收敛，再启动下一台。
5. 所有节点稳定后保存一次集中采集结果，作为冷启动基线。

## 六、分层验收

### 6.0 固定角色和路由来源门禁

该门禁用于确认测试使用的是固定的边缘/内部架构，并确认 MIDR 业务路由没有被边缘 BGP 的替代路径掩盖。

1. 每台 MIDR 按角色表检查进程：

~~~bash
pgrep -a midrd
pgrep -a zebra
~~~

8 台边缘 MIDR 必须有 `bgpd`、Provider 和本站 BGP-R（TEIN 为 TEIN-B1）的 Established 邻居；2 台内部 MIDR 和 2 台专职 bootstrap 必须没有 `bgpd` 或 Provider。

2. 每台 MIDR 检查本站 BGP-R 默认网关和所有 bootstrap、群代表 locator：

~~~bash
ip -6 route show default
. /etc/midr/node.env
ip -6 route get <每个bootstrap或候选locator> \
  from "$MIDR_LOCATOR" ipproto tcp dport 5871
ping -6 -c 3 <每个bootstrap或候选locator>
~~~

3. 在 BGP-R 上确认本地和远端 transport 前缀均有双向路径。如果 BGP-R 当前依赖内部 MIDR 的 BGP 邻居学习本站地址，必须先改为 BGP-R 的 connected/static 路由或受控发布策略；内部 MIDR 不得为了发布 transport 前缀而临时启动 `bgpd`。

4. 业务 Prefix 收敛后检查路由来源：

~~~bash
ip -6 route show proto 199
ip -6 route show proto bgp
ip -6 route get <远端业务地址> from <本地业务地址>
~~~

业务 Prefix 必须由 MIDR 生成的 `proto 199` 路由承载。边缘 BGP 可以交换外部前缀和角色表规定的边界前缀，但不得为内部 MIDR 测试 Prefix 提供更优的 `proto bgp` 替代路径。

5. 对一个测试 Prefix 执行 Provider withdraw，确认远端 `proto 199` 路由和业务 Ping 随之撤销；撤销后 transport-address 仍应可达。该测试验证控制面 underlay 可达性与 MIDR 业务路由是两个独立层次。

固定角色门禁通过条件是：边缘/内部进程与配置符合角色表，内部节点没有 `bgpd`，所有 transport-address 经本站 BGP-R 可达，业务 Prefix 由 MIDR `proto 199` 安装，且 withdraw 后业务路由消失。

### 6.1 Underlay 验收

每个 MIDR 节点至少满足：

~~~bash
. /etc/midr/node.env
ip -6 route get <每个bootstrap-locator> \
  from "$MIDR_LOCATOR" ipproto tcp dport 5871
ping -6 -c 3 <每个bootstrap-locator>
ss -ltnp | grep ':5871'
~~~

route get 显示本站网关和 table 1990；后续路径可以经过 T1 或 TEIN 路由器，不要求 MIDR 节点物理直连。该查询验证本机选路，Session 和双向探测验证端到端可达性。

### 6.2 Bootstrap 验收

bootstrap 节点执行：

~~~text
show midr self
show midr neighbors
show midr bootstrap-seeds
~~~

预期：

- Capabilities 包含 Bootstrap；
- 群号为 0；
- 配置的 bootstrap 骨干 Session 为 Established；
- bootstrap 节点之间的连接来源为固定基础设施配置；
- 不运行 bgpd 和 Prefix Provider；
- 不要求 bootstrap 作为普通业务成员发布同群 Node/Link，业务 GRE/FIB 标为不适用；
- bootstrap 上的 Prefix/SPF 总数不作为业务转发能力证据。

### 6.3 普通节点自动加入验收

普通节点执行：

~~~text
show midr self
show midr join
show midr neighbors
show midr directory
show midr bootstrap-seeds
~~~

预期：

- Active locator 等于本机 transport-address；
- show midr join 完成代表探测、群组选择和成员发现；
- 普通节点不需要为所有其他成员配置 midr session；
- 自动建立的同群或挂靠 Session 为 Established；
- show midr directory 中的成员 locator、群号和能力位与角色表一致；
- 重启后 bootstrap seed 可以从持久状态恢复。

### 6.4 Node、Link、TED 和 SPF 验收

每个成员节点执行：

~~~text
show midr nodes
show midr links
show midr spf
show midr virtual-links
~~~

预期：

- Node 目录包含本群成员和预期远端节点；
- `show midr links` 中预期探测对象为 up，RTT、丢包和 admission 状态可读；该表包含候选和锚点的 PM 测量，不能直接把 up 行数视为 TED 中有效拓扑边的数量；
- 同群业务 Prefix 在 SPF 中显示为 local 或 intra；
- 多群组存在有效群间 Link 时，跨群业务 Prefix 显示为 inter；
- 每条预期虚链路为 READY 且 overlay reachable。

当前源码已经实现 INTER_GROUP SPF scope、群间 group graph 和跨群路由安装。运行时验收不能只看 show midr spf 的总数，必须检查跨群 Prefix 的具体 route、下一跳和 FIB。

边缘节点的 Prefix Provider 可把本地 BGP RIB 中的外部前缀作为本节点发布的 Prefix 输入 MIDR，因此 SPF 的 `local` 不等于该前缀直接连接在本机接口上，也不能证明跨群转发成功。跨群选路验收应选择远端发布的前缀，并核对业务流量使用的 GRE 下一跳；内部节点没有本地 BGP 输入，更便于检查 MIDR 路由是否实际安装。

### 6.5 FIB 和业务流量验收

业务路由安装后，再按控制报文的协议和端口查询 bootstrap 与邻居。以下命令在目标 MIDR 节点执行，以武汉 bootstrap 和复旦为查询目标：

~~~bash
. /etc/midr/node.env
ip -6 rule show
ip -6 route show table 1990
ip -6 route get 240a:a00f:800:3::2 \
  from "$MIDR_LOCATOR" ipproto tcp dport 5859
ip -6 route get 240a:a00f:100:1::2 \
  from "$MIDR_LOCATOR" ipproto tcp dport 5871
ip -6 route get 240a:a00f:100:1::2 \
  from "$MIDR_LOCATOR" ipproto udp dport 5860
~~~

远端控制与探测查询应显示本站网关、ens5 和 table 1990；查询本机地址时显示 local 属于正常结果。普通 `route get` 不带协议、端口时查询的是业务选路，可能指向 GRE，不能据此判定 transport 隔离失败。GRE 外层的策略规则应为本机 locator、`ipproto gre` 和 table 1990，可结合 ens5 抓包与双向 overlay 探测核验。

每个业务源节点至少选择一个同群目标和一个跨群目标：

~~~bash
ip -6 route show proto 199
ip -6 route get <同群远端业务地址> from <本地业务地址>
ip -6 route get <跨群远端业务地址> from <本地业务地址>
ping -6 -c 3 -W 2 -I <本地业务地址> <同群远端业务地址>
ping -6 -c 3 -W 2 -I <本地业务地址> <跨群远端业务地址>
~~~

每个目标必须同时满足：

1. SPF route 可达并带有 nexthop；
2. Linux FIB 中存在对应 proto 199 路由；
3. route get 实际选择预期接口和下一跳；
4. 指定业务源地址的双向 Ping 成功。

如果内部 MIDR 的 `route get` 显示 `proto bgp`，或业务 Prefix 同时存在边缘 BGP 的替代路径，该结果不能作为 MIDR 路由验收通过；应先撤销替代路径，重新执行 6.0 的角色和路由来源门禁。

只看到 underlay transport-address 可达，不能代替业务 Prefix 验收。

## 八、故障和持久化验收

### 8.1 普通节点重启

保存当前状态后，重启一个普通节点：

~~~bash
systemctl restart midrd.service
~~~

服务在启动后自动重新加载 /etc/midr/node.commands。不得删除：

~~~text
/var/lib/midr/<node-id>.seq
/etc/midr/node.commands
~~~

预期：节点以更高 sequence 重新加入，不产生旧对象复活，Session、Node、Link、SPF、FIB 和业务流量恢复。

### 8.2 bootstrap 故障

停止一个 bootstrap，集中采集以下结果：

~~~text
show midr neighbors
show midr bootstrap-seeds
show midr join
~~~

预期：普通节点继续使用其他 bootstrap 候选；若所有 bootstrap 都不可达，普通节点应明确进入降级状态，不能把未建立的 Session 当作成功。

### 8.3 GRE 虚链路故障

在已确认接口名后删除一条虚接口：

~~~bash
ip link del <mgre-interface>
~~~

预期是接口重新创建、overlay 地址和 proto 199 路由恢复，业务流量重新连通。这个测试验证虚链路自愈，不代替 Session、SPF 或跨群选路验收。

## 九、停止和回滚

停止顺序为普通成员、群代表、bootstrap、MIDR Zebra；边缘 MIDR 的 `bgpd` 按角色表保留或单独停止，内部 MIDR 不需要恢复 `bgpd`。保留发布目录、node.commands、sequence、集中采集结果和日志。BGP-R、P、TEIN-B1、TEIN-B2 的 underlay FRR 不属于本实验的停止对象；除非另有维护计划，不得因 MIDR 测试停止这些 underlay 进程。

回滚时恢复上一版匹配的 midrd、zebra 和共享库组合，继续使用原有 node.commands 和 sequence 文件。回滚后重新执行 underlay、bootstrap、普通成员和业务 Prefix 的集中检查。
