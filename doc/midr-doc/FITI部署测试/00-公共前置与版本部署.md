## 2. 环境边界

FITI 架构中的 BGP-R、TEIN 边界和 TEIN 内部路由器负责 underlay IP 转发。它们运行现有的 zebra、bgpd 和/或 ospf6d，不是本实验新增的 MIDR 节点。每台 MIDR 节点的本站 BGP-R 是 transport-address 的第一跳；内部 MIDR 节点可以不运行 bgpd，但必须有经本站 BGP-R 的默认路由或等效的 underlay 路由。

本实验的版本边界固定为：MIDR 节点使用本发布包中的 FRR 10.7.0-dev `zebra`、原版 FRR 10.7.0-dev `bgpd`、`vtysh` 和独立 `midrd`；外部 BGP-R 节点继续使用现有 FRR 8.4.4。两者位于不同主机，通过标准 BGP-4/TCP 179 互操作，不共享 `libfrr` 或 Zebra 进程。不要把 FRR 8.4.4 的单个 `bgpd` 二进制放进 10.7 发布包。

部分站点可能过滤 ICMP。ping 失败不能单独证明节点不可达；以 SSH、ip -6 route get、TCP 5871、服务状态和日志为准。PPT 约定 60-ens4.yaml 为带外管理配置，61-l3.yaml 为三层互联配置。部署脚本只检查这两个文件，不修改它们。

FRR 配置状态异常时使用 systemctl restart frr，不要只依赖 reload 清理旧状态。MIDR 切换前必须明确旧 FRR 是否停止，不能让旧 zebra 与匹配版本 zebra 同时管理同一 Linux FIB。

## 3. 进程和客户端总览

| 程序或服务 | 是否常驻 | 作用 | 启动方式 |
|---|---:|---|---|
| zebra | 是 | 管理 Linux 接口、路由和 ZAPI；必须与 midrd 使用匹配发布包 | midr-zebra.service |
| bgpd | 边缘节点是，内部节点和专职 bootstrap 否 | 边缘 MIDR 与本站 BGP-R 交换既定外部路由 | midr-bgpd.service，仅 MIDR_EDGE_BGP=yes |
| midr-bgp-prefix-provider.py | 仅边缘节点常驻 | 读取本站有效 BGP RIB，通过 Prefix IPC 交给 midrd | midr-bgp-prefix-provider.service |
| midrd | 是 | MIDR Session、目录、Link、分群、SPF、GRE 和 MIDR FIB | midrd.service |
| vtysh | 否 | 当前发布包的统一 VTY 客户端，可查询 midrd、zebra 和 bgpd | 日常交互和单次查询 |
| midrd-vty.py | 否 | 直接连接 midrd socket 的 Python 客户端 | 现有启动配置加载、集中采集和备用查询 |

正式职责分为三类：8 台边缘 MIDR 运行 zebra + bgpd + midrd + Prefix Provider，2 台内部业务 MIDR 和 2 台专职 bootstrap 运行 zebra + midrd。Bootstrap 固定群号 0，不承担业务 GRE/FIB；初始群代表为北航（Group 1）和复旦（Group 2）。原有系统 frr.service 是一个服务编排入口，可能管理系统版本的多个 daemon；当前发布包中的 zebra、bgpd、midrd 是独立可执行文件，不会因为启动 midrd 就自动启动其他 daemon。部署脚本会停止并禁用旧 frr.service，再安装匹配版本的独立 systemd 服务。

vtysh 和 midrd-vty.py 都是客户端，不需要常驻进程，也不会替代 daemon。当前发布包的 vtysh 已注册 midrd，可直接执行 show midr 命令；使用 /opt/midr-current/vtysh 和 /run/midr，不使用系统 FRR 8.4.4 的 vtysh 连接本发布包。/run/midr/midrd.vty 是 midrd 创建的运行时 Unix socket，不是配置文件。

### 3.1 MIDR 与其他路由来源的选择顺序

当前代码通过 Zebra ZAPI 为 MIDR 路由设置管理距离 115（`ZEBRA_BGP_MIDR_DISTANCE_DEFAULT`）。常见默认值为：直连 0、静态 1、eBGP 20、OSPF 110、MIDR 115、iBGP 200。Zebra 先比较管理距离，再比较同一来源内的 metric；因此不能简单说“BGP 总是优先于 MIDR”。只有 MIDR SPF 已经算出有效下一跳并把路由提交给 Zebra 时，才会参与这个比较；`show midr spf` 中标为 `unreachable` 或没有下一跳的前缀不会安装到 FIB。

当前版本没有把 MIDR 管理距离做成 VTY 或命令行开关。不要通过修改全局 BGP distance 来模拟 MIDR 策略，因为这会同时改变 underlay BGP 的选路。后续如需策略切换，开关应放在 `midrd`，由 `midrd` 将经过校验的 distance 通过 ZAPI 传给 Zebra，并保留 115 作为默认值；这属于独立功能变更，不是本轮部署参数。

### 3.2 Transport 与业务路由隔离

正式服务在启动 midrd 前，由 `ExecStartPre` 执行 `/usr/local/libexec/midr/setup-midr-underlay.py`。脚本读取 `MIDR_LOCATOR`、`MIDR_GATEWAY` 和 `MIDR_UNDERLAY_INTERFACE`（默认 `ens5`），在 IPv6 路由表 1990 中配置本地传输网段和本站网关。优先级 19900～19905 的规则将本机 locator 发出的 TCP 5859/5871、UDP 控制/PM/路径探测和 GRE 外层报文送入该表。业务地址的流量继续使用 main 表中的 BGP/MIDR 路由，不需要配置全部远端 locator。

Transport locator 是协议端点，不能同时作为应用 UDP 业务源地址。路由表 1990 是 underlay 转发选择；`proto 199` 是 main 表中 MIDR 业务路由的来源标记，两者含义不同。脚本在每次启动或重启时重新加载规则，并检查保留的表号和规则优先级是否存在冲突；不修改 Netplan 或带外管理接口。

在已安装节点上检查隔离规则和控制会话出口：

~~~bash
. /etc/midr/node.env
ip -6 rule show
ip -6 route show table 1990
ip -6 route get 240a:a00f:100:1::2 \
  from "$MIDR_LOCATOR" ipproto tcp dport 5871
~~~

远端控制连接应显示经本站网关、`ens5` 和 table 1990 转发。查询本机地址时显示 local 属于正常结果。不带协议和端口的 `route get` 查询业务选路，不能用它代替控制报文出口检查。

## 5. 在 90 构建发布包

以下命令在 FITI-90 的 FRR 源码目录执行。构建结果必须同时包含 midrd、匹配版本 zebra、匹配版本 bgpd、vtysh、VTY 客户端、启动包装器和共享库。

### 5.1 `RELEASE_ID` 的设置方式

`RELEASE_ID` 是本次发布包的唯一标识，由源码提交短哈希和 UTC 构建时间组成。它会用于发布目录名，例如 `/tmp/midr-5228cff9b3be-20261001T154159Z`。每次构建新版本时，在 90 的当前 shell 中执行：

~~~bash
cd /home/guest/yhy/frr
export RELEASE_ID="$(git rev-parse --short=12 HEAD)-$(date -u +%Y%m%dT%H%M%SZ)"
printf 'RELEASE_ID=%s\n' "$RELEASE_ID"
export RELEASE_DIR="/tmp/midr-$RELEASE_ID"
printf 'RELEASE_DIR=%s\n' "$RELEASE_DIR"
~~~

完成打包并上传后，部署脚本使用 `RELEASE_SRC` 指向由 `RELEASE_ID` 生成的发布目录：

~~~bash
export RELEASE_SRC="/tmp/midr-$RELEASE_ID"
test -f "$RELEASE_SRC/RELEASE_ID"
test -f "$RELEASE_SRC/SHA256SUMS"
cat "$RELEASE_SRC/RELEASE_ID"
~~~

如果重新登录 90，变量不会自动保留。此时把实际目录名填入下面的命令，目录名必须与 `ls -d /tmp/midr-*` 显示的名称一致：

~~~bash
export RELEASE_SRC=/tmp/midr-5228cff9b3be-20261001T154159Z
export RELEASE_ID="$(cat "$RELEASE_SRC/RELEASE_ID")"
printf 'RELEASE_SRC=%s\nRELEASE_ID=%s\n' "$RELEASE_SRC" "$RELEASE_ID"
test -f "$RELEASE_SRC/SHA256SUMS"
~~~

~~~bash
cd /home/guest/yhy/frr
git status --short --branch
git rev-parse HEAD
make -j"$(nproc)" midrd/midrd zebra/zebra bgpd/bgpd vtysh/vtysh

rm -rf "$RELEASE_DIR"
install -d -m 755 "$RELEASE_DIR/lib"

cp -L midrd/.libs/midrd "$RELEASE_DIR/midrd"
cp -L zebra/.libs/zebra "$RELEASE_DIR/zebra"
cp -L bgpd/.libs/bgpd "$RELEASE_DIR/bgpd"
# vtysh/vtysh 是 libtool 启动包装器；发布包必须复制实际 ELF。
cp -L vtysh/.libs/vtysh "$RELEASE_DIR/vtysh"
cp -L doc/midr-doc/deployment-tools/midrd-vty.py \
  "$RELEASE_DIR/midrd-vty.py"

cat >"$RELEASE_DIR/run-midrd.sh" <<'EOF'
#!/bin/sh
set -eu
BASE_DIR=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd -P)
export LD_LIBRARY_PATH="$BASE_DIR/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
exec "$BASE_DIR/midrd" "$@"
EOF

chmod 0755 "$RELEASE_DIR"/midrd "$RELEASE_DIR"/zebra \
  "$RELEASE_DIR"/bgpd "$RELEASE_DIR"/vtysh \
  "$RELEASE_DIR"/run-midrd.sh "$RELEASE_DIR"/midrd-vty.py

printf '%s\n' "$RELEASE_ID" >"$RELEASE_DIR/RELEASE_ID"
git rev-parse HEAD >"$RELEASE_DIR/GIT_COMMIT"
(cd "$RELEASE_DIR" && \
  find . -type f ! -name SHA256SUMS ! -name RELEASE_ID ! -name GIT_COMMIT \
    -printf '%P\n' | sort | xargs sha256sum) >"$RELEASE_DIR/SHA256SUMS"
~~~

最终目录至少应为：

~~~text
midrd  zebra  bgpd  vtysh  run-midrd.sh  midrd-vty.py
lib/   RELEASE_ID  GIT_COMMIT  SHA256SUMS
~~~

检查动态库依赖时逐个执行：

~~~bash
for binary in midrd zebra bgpd vtysh; do
  echo "Checking $RELEASE_DIR/$binary"
  output=$(LD_LIBRARY_PATH="$RELEASE_DIR/lib" \
    ldd "$RELEASE_DIR/$binary" 2>&1)
  printf '%s\n' "$output"
  if printf '%s\n' "$output" | grep -Fq 'not found'; then
    echo "MISSING DEPENDENCY: $binary" >&2
    exit 1
  fi
done

(cd "$RELEASE_DIR" && sha256sum -c SHA256SUMS)
~~~

zebra 依赖 libmlag_pb.so.0 等库时，必须把实际缺失的非系统库放入 lib/，不能只复制一个二进制。生成 `SHA256SUMS` 时会把 `lib/` 下的共享库一并纳入清单。发布包通过 SSH 上传到 90 的 /tmp 后设置：

~~~bash
export RELEASE_SRC="$RELEASE_DIR"
test -f "$RELEASE_SRC/SHA256SUMS"
~~~

以后每次发布都使用新的 RELEASE_ID 和新的目录，不覆盖旧目录。旧目录用于回滚。

## 7. 单节点和批量安装

部署脚本从 90 执行，RELEASE_SRC 必须指向本次完整发布目录：

`deploy-node-from-90.sh` 是 90 管理机上的入口：读取清单和节点配置，预先校验发布包，建立临时 staging 目录，通过 SSH/SCP 复制文件，然后调用目标节点上的 `install-node-local.sh`。`install-node-local.sh` 才是目标节点上的实际安装器，负责检查本机地址、默认路由、旧 FRR 状态和发布包，备份现状，停止旧进程，安装新文件和 systemd 单元，启动匹配版本并执行启动后验收。它不是需要长期运行的 daemon；执行结束后临时 staging 目录会被删除。

`--mode check` 只执行发布包和目标节点前置检查，不停止进程、不写入持久配置。`--mode apply` 的顺序是：

~~~text
90 本地预检
  -> 目标节点临时 staging
  -> 目标节点备份 /etc/frr、/etc/netplan、/etc/midr、服务状态和路由
  -> 停止 midrd、bgpd、zebra，再停止旧 frr.service
  -> 安装完整发布包、node.env、node.commands 和 systemd 单元
  -> 启动 zebra，再启动边缘节点 bgpd，最后启动 midrd
  -> 等待 socket、检查运行中的 ELF 路径和 MIDR VTY
  -> 失败时使用本次备份恢复旧 FRR 和服务
~~~

`apply` 会停止旧进程并启动新进程；正常情况下不需要手工执行 `kill`。安装器会等待旧的 `frr.service` 和 zebra/bgpd/midrd 进程完全退出，并在确认没有旧进程后才启动新服务。如果同一发布目录在目标节点上已经存在但不完整，安装器会在停止服务前拒绝继续，避免在不完整发布包上切换。应改用新的 `RELEASE_ID`，或清理确认无进程使用的残缺目录后重试。

~~~bash
# 沿用第 5 节已经设置的 RELEASE_SRC；如果重新登录 90，先按第 5.1 节恢复它。
test -f "$RELEASE_SRC/SHA256SUMS"

bash midr-test/fiti-deploy/deploy-node-from-90.sh \
  --node MIDR_fudan --mode check

bash midr-test/fiti-deploy/deploy-node-from-90.sh \
  --node MIDR_fudan --mode apply
~~~

check 只做目标机校验和发布包校验，不停止现有服务；apply 会备份现状、停止旧 FRR/MIDR、安装完整发布包、安装 systemd 单元并启动匹配版本。

12 节点按 bootstrap、representatives、members 分阶段执行：

~~~bash
# 沿用前面已经设置并校验过的 RELEASE_SRC。
test -f "$RELEASE_SRC/SHA256SUMS"

bash midr-test/fiti-deploy/deploy-batch-from-90.sh \
  --phase bootstrap --mode check
bash midr-test/fiti-deploy/deploy-batch-from-90.sh \
  --phase bootstrap --mode apply

bash midr-test/fiti-deploy/deploy-batch-from-90.sh \
  --phase representatives --mode check
bash midr-test/fiti-deploy/deploy-batch-from-90.sh \
  --phase representatives --mode apply

bash midr-test/fiti-deploy/deploy-batch-from-90.sh \
  --phase members --mode check
bash midr-test/fiti-deploy/deploy-batch-from-90.sh \
  --phase members --mode apply
~~~

批量脚本默认遇到失败节点就停止。只有查看该节点日志并确认不会掩盖阶段性错误后，才使用 --continue。阶段日志写入 fiti-deploy-<UTC时间>/。

## 8. 持久配置和 VTY 加载

### 8.1 启动时的配置加载

/etc/midr/node.commands 是持久 VTY 配置，包含本机 transport-address、bootstrap、角色、群组和必要的固定 bootstrap Session。midrd.service 启动时，由 ExecStartPost 调用 /usr/local/libexec/midr/load-midrd-config.sh，等待 /run/midr/midrd.vty 可用后，通过 midrd-vty.py 执行该文件。正常启动或重启不需要再次手工加载配置。

### 8.2 日常 MIDR 查询：vtysh

以下命令在目标 MIDR 节点执行。每次打开新终端时设置当前发布目录和动态库路径：

~~~bash
export MIDR_DIR=/opt/midr-current
export LD_LIBRARY_PATH="$MIDR_DIR/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"

# 统一交互入口：连接当前运行的 midrd、zebra 和 bgpd
"$MIDR_DIR/vtysh" --vty_socket /run/midr
~~~

进入交互界面后执行：

~~~text
show daemons
show midr self
show midr join
show midr neighbors
show midr nodes
show midr directory
show midr links
show midr virtual-links
show midr spf
show midr running-config
exit
~~~

只连接 midrd 的交互入口：

~~~bash
"$MIDR_DIR/vtysh" --vty_socket /run/midr -d midrd
~~~

单次查询不进入交互界面；每个 -c 对应一条命令，可重复指定。-f 按配置模式处理文件，不用于加载 show 查询清单：

~~~bash
"$MIDR_DIR/vtysh" --vty_socket /run/midr -d midrd \
  -c 'show midr self' \
  -c 'show midr join' \
  -c 'show midr neighbors' \
  -c 'show midr virtual-links' \
  -c 'show midr spf'
~~~

### 8.3 查询 Zebra、BGP 和内核 FIB

沿用 8.2 节的 MIDR_DIR 和 LD_LIBRARY_PATH：

~~~bash
# Zebra：全部 IPv6 路由，以及一个业务前缀的路由来源、管理距离和 SPF metric
"$MIDR_DIR/vtysh" --vty_socket /run/midr -d zebra \
  -c 'show ipv6 route'
"$MIDR_DIR/vtysh" --vty_socket /run/midr -d zebra \
  -c 'show ipv6 route 240a:a00f:300::/48'

# 仅边缘 MIDR 运行 bgpd
"$MIDR_DIR/vtysh" --vty_socket /run/midr -d bgpd \
  -c 'show bgp ipv6 unicast summary'
"$MIDR_DIR/vtysh" --vty_socket /run/midr -d bgpd \
  -c 'show bgp ipv6 unicast 240a:a00f:300::/48'

# Linux FIB：实际安装的 MIDR 路由
ip -4 route show proto 199
ip -6 route show proto 199
~~~

内部节点和专职 bootstrap 不运行 bgpd；在这些节点使用 -d bgpd 显示未运行符合角色配置。Zebra 的 show ipv6 route 中显示 [distance/metric]；Linux ip route 中的 metric 20 是 Zebra 固定的内核安装优先级，不代表 SPF 路径代价。

### 8.4 Python 客户端和配置操作的边界

当前发布包可以用 vtysh 查询 MIDR。midrd-vty.py 仍由启动加载脚本和集中采集脚本使用，也可直接查询同一个 midrd：

~~~bash
python3 /opt/midr-current/midrd-vty.py --socket /run/midr/midrd.vty
python3 /opt/midr-current/midrd-vty.py --socket /run/midr/midrd.vty \
  -c 'show midr self' -c 'show midr join'
~~~

show 命令用于查询。--commands-file 会执行文件内的每条命令；/etc/midr/node.commands 含配置命令，重复加载可能重新触发入群、探测和收敛，不能作为日常查看状态的步骤。只有在明确需要恢复或应用配置时，才手工执行：

~~~bash
python3 /opt/midr-current/midrd-vty.py \
  --socket /run/midr/midrd.vty \
  --commands-file /etc/midr/node.commands
~~~

配置加载后检查 show midr self、show midr join、show midr neighbors 和 show midr virtual-links；不能仅凭“开始加入”的回显判断入群结果。持久修改写入 /etc/midr/node.commands，再按计划重启 midrd.service。交互修改会立即作用于运行状态；当前部署不依靠 vtysh 的 write memory 自动回写 node.commands。

## 9. 日常启动、停止、重启

在目标节点执行：

~~~bash
systemctl status midr-zebra.service midr-bgpd.service midrd.service --no-pager
systemctl is-active midr-zebra.service midrd.service

systemctl restart midrd.service
systemctl stop midrd.service
systemctl start midrd.service

# 仅边缘 MIDR 使用 bgpd；内部节点不要启动它
systemctl restart midr-bgpd.service
systemctl stop midr-bgpd.service

# 只有在需要重启匹配 Zebra 时执行；它会影响 midrd 的 ZAPI 和 FIB
systemctl restart midr-zebra.service
~~~

修改 node.commands 后，先编辑文件，再执行 systemctl restart midrd.service；服务会重新加载持久配置。不要删除 /var/lib/midr/<node-id>.seq，避免 sequence 回退。查看日志：

~~~bash
journalctl -u midr-zebra.service -n 100 --no-pager
journalctl -u midr-bgpd.service -n 100 --no-pager
journalctl -u midrd.service -n 100 --no-pager
tail -n 100 /var/log/midr/*-midrd.log
ss -ltnp | grep ':5871' || true
ss -xl | grep /run/midr || true
~~~

## 10. 通用验收和故障顺序

按以下顺序检查，避免把控制面、GRE 和业务路由混为一项：

~~~bash
systemctl is-active midr-zebra.service midrd.service
test -S /run/midr/zserv.api
test -S /run/midr/midrd.vty
ss -ltnp | grep ':5871'
export MIDR_DIR=/opt/midr-current
export LD_LIBRARY_PATH="$MIDR_DIR/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
"$MIDR_DIR/vtysh" --vty_socket /run/midr -d midrd \
  -c 'show midr self' \
  -c 'show midr join' \
  -c 'show midr neighbors' \
  -c 'show midr nodes' \
  -c 'show midr links' \
  -c 'show midr spf' \
  -c 'show midr virtual-links'
~~~

如果 midrd 初始化失败，先确认匹配 Zebra 的 /run/midr/zserv.api 存在，再确认服务二进制和 lib/ 来自同一发布包。若 Session 没有建立，先执行 ip -6 route get <locator> from <本机locator> ipproto tcp dport 5871 和 ss -tnp | grep ':5871'，再查 journalctl 和 MIDR 日志。若 GRE 已 READY 但业务不通，检查 ip route show proto 199、ip route get 的实际出口和业务 Prefix 是否被 underlay 更优路由覆盖。

## 11. 升级、回滚和配置持久性

升级使用新的完整发布目录和相同的单节点/批量 apply 流程。不要只替换 midrd，也不要混用不同版本的 zebra、bgpd、vtysh 或共享库。旧 /opt/midr-releases/midr-* 目录保留，/opt/midr-current 只作为当前版本指针。

安装器在 /var/lib/midr/deploy-backups/<timestamp>-<node>/ 保存 /etc/frr、Netplan、/etc/midr、服务状态、进程和路由表。查看最近备份：

~~~bash
ls -1dt /var/lib/midr/deploy-backups/* | head
cat /var/lib/midr/last-deploy-backup
~~~

回滚必须同时恢复与 midrd 匹配的 zebra、bgpd 和 lib/，并恢复 /etc/midr/node.env、node.commands 和服务文件。恢复后按 zebra -> bgpd（边缘） -> midrd 顺序启动，并重新执行 Session、GRE、SPF 和 FIB 验收。

## 12. 配置参数的含义

| 参数 | 含义 |
|---|---|
| --node-id | 本节点稳定的 MIDR 数字身份 |
| --listen '[locator]:5871' | MIDR TCP 控制面监听地址 |
| --zserv-path | midrd 连接匹配 Zebra 的 ZAPI socket |
| --vty_socket | VTY socket 所在目录 |
| --sequence-file | 持久化 MIDR 序列号文件 |
| --pidfile | 运行时 PID 文件 |
| --takeover-delay、--lifetime、--hold-time | 会话接管、存活和保持计时器 |
| MIDR_EDGE_BGP | yes 启用边缘 bgpd，no 禁用 |
| MIDR_PREFIX_MODE | none 不接 Prefix Provider，socket 使用 --prefix-socket |
| MIDR_PREFIX_MAX_AS_PATH_LENGTH | BGP 前缀导出到 MIDR 的最大 AS_PATH 长度，默认 1；不改变 bgpd 自身路由表 |
| MIDR_GATEWAY | 本站 underlay 网关，用于 transport 专用路由表 |
| MIDR_UNDERLAY_INTERFACE | transport 出口接口，默认 ens5 |

--no-zebra、--peer、--link 和 --link-addr 只属于早期两节点调试或手工联调，不属于正式 systemd 部署参数。正式部署不依赖手工创建 mgre-* 接口；虚链路由 MIDR 根据已建立的 Session、Link 和 Prefix 状态自动创建。
