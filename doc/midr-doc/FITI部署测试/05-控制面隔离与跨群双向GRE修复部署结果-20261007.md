## 2. 修复内容

### 2.1 Transport 与业务 FIB 隔离

`midrd.service` 在 `ExecStartPre` 执行 `/usr/local/libexec/midr/setup-midr-underlay.py`，根据本机 locator、本站网关和出口接口建立 IPv6 表 1990。本机 locator 发出的 TCP 5859/5871、UDP 控制/PM/路径探测和 GRE 外层使用该表；业务流量继续使用 main 表。规则优先级为 19900～19905，规则协议标记为 199。

该隔离使控制会话和 GRE 外层不依赖 MIDR 业务汇总路由，避免业务前缀覆盖 transport 地址后形成递归。规则不依赖远端邻居清单，并随服务启动、重启重复加载。表 1990 与 main 表中业务路由的 `proto 199` 来源标记含义不同。locator 用于协议传输，不作为应用 UDP 业务源地址。部署不修改带外接口或 Netplan 文件。

### 2.2 跨群接收端的 PM/GRE

接收端接受跨群、非 ATTACH 的 `PEER_REQ_REPLY` 请求后，登记请求中的节点身份和 locator，启动 PM 并形成反向 GRE。该过程不把对端标记成同群邻接。专职 bootstrap 和 ATTACH 会话保持控制面用途，不创建业务 PM/GRE。

候选清理和换群清理保留已建立的跨群锚点及其接收端链路，避免保留 Session 却删除 PM/GRE。

### 2.3 群代表角色随群变化

代表身份属于所在群。节点直接换群时清除旧群代表身份；在同一群落定时保留合法代表身份。回归覆盖跨群接收、bootstrap/ATTACH 排除、7→8 换群卸任以及 8→8 同群保留。

### 4.1 真实本地前缀的跨群发布和撤销

使用乌鲁木齐 ens5 上真实存在的直连网段 `240a:a00f:300:1::/64`。通过既有 Prefix IPC 临时发布该前缀，同时保留原 BGP 前缀快照；测试结束恢复正式 BGP Provider。未新增接口、地址或静态业务路由。

发布时，乌鲁木齐显示该前缀为 `local`；其余 9 台业务节点均计算出 `inter` 路由并安装 `proto 199`。专职 bootstrap 不安装业务 FIB。武汉 R2、郑州 R2 到乌鲁木齐真实地址 `240a:a00f:300:1::2` 的 Ping 均为 3/3 成功，选路走 MIDR GRE。

代表性下一跳如下：

| 查询节点 | SPF 类型 | 第一跳 |
|---|---|---|
| 北航 | inter | 乌鲁木齐，`mgre-67000000` |
| 昆明 | inter | 乌鲁木齐，`mgre-67000000` |
| 武汉 R2 | inter | 北航，`mgre-66000000` |
| 郑州 R2 | inter | 武汉 R2，`mgre-6b000000` |

即使目的地址同时也是远端 locator，普通 ICMP 业务仍走 main 表中的 MIDR 路由；TCP 5871 控制查询保持经本站网关、表 1990。

恢复正式 Provider 后，全网该 `/64` 的 SPF 条目和 `proto 199` 路由均消失。原有 `/48` 汇总与 underlay 路由仍存在，因此撤销特定 `/64` 不要求全部地址连通性消失。本轮验收确认该前缀的跨群传播、有效下一跳、FIB 安装、实际转发和精确撤销。
