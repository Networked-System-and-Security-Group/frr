# 04 单节点部署、运维与自动化手册

本文说明一台 FITI MIDR 路由器从发布包安装到日常运维的完整流程。本文可以独立执行；多节点上线顺序和整网验收见 03 文档。所有正式进程由 systemd 管理，节点配置保存在 /etc/midr，发布包按版本保存在 /opt/midr-releases。

## 1. 工作模型

一台 MIDR 主机上的正式进程关系如下：

~~~text
midr-zebra.service
        |
        +-- midr-bgpd.service       仅边缘 MIDR
        |
        +-- midrd.service
                |
                +-- ExecStartPre 配置 transport 专用路由表 1990
                +-- ExecStartPost 加载 /etc/midr/node.commands
                +-- midr-bgp-prefix-provider.service  仅边缘 MIDR
~~~

zebra 负责通过 ZAPI 管理 Linux 路由表和接口。midrd 负责 MIDR Session、节点目录、Link、群组、SPF、GRE 虚链路和 MIDR 路由。边缘 MIDR 还运行匹配版本的 bgpd，与本站 BGP-R 交换边界路由；内部 MIDR 不运行 bgpd，只通过本站 BGP-R 提供的默认路由或等效 underlay 路由访问 transport-address。

vtysh 和 midrd-vty.py 都是一次性客户端，不是常驻进程。vtysh 查询 zebra/bgpd 的 VTY；midrd-vty.py 连接 /run/midr/midrd.vty，加载或查询 midrd。启动 midrd 不会自动启动 zebra 或 bgpd。

## 2. 目录和文件

| 路径 | 内容 | 是否持久 |
|---|---|---|
| /opt/midr-releases/midr-${RELEASE_ID}/ | 一个完整、不可覆盖的发布包 | 是 |
| /opt/midr-current | 指向当前发布包的符号链接 | 是 |
| /etc/midr/node.env | 本机 node-id、locator、角色、网关和服务变量 | 是 |
| /etc/midr/node.commands | 本机 VTY 配置、bootstrap 和角色配置 | 是 |
| /etc/midr/zebra.conf | 匹配发布包的 Zebra 配置 | 是 |
| /etc/midr/bgpd.conf | 边缘 MIDR 的 BGP 配置 | 是 |
| /usr/local/libexec/midr/ | systemd 使用的启动和配置加载脚本 | 是 |
| /usr/local/libexec/midr/setup-midr-underlay.py | 启动前配置本节点 transport 策略路由 | 是 |
| /var/lib/midr/<node-id>.seq | MIDR 序列号持久文件 | 是 |
| /var/lib/midr/deploy-backups/ | 每次 apply 前的配置、服务和路由备份 | 是 |
| /var/log/midr/ | zebra、bgpd、midrd 日志 | 是 |
| /run/midr/ | PID、VTY、ZAPI 等运行时文件 | 否，重启后重新生成 |

node.commands 和 sequence 文件不能因为重启或升级而删除。/run/midr/midrd.vty 是 Unix socket，不是配置文件；它只有在 midrd 正常运行后才存在。

`midrd.service` 每次启动都会先加载 underlay 表 1990 和优先级 19900～19905 的规则，使本机 locator 发出的 MIDR TCP、UDP 探测和 GRE 外层报文经本站网关转发。main 表继续承担业务路由。该操作只使用本机 locator、网关和出口接口，不需要维护所有邻居地址；完整规则和查询命令见 00 文档 3.2 节。

## 3. 节点配置文件

90 上的节点清单位于：

~~~text
midr-test/fiti-deploy/nodes-12.csv
midr-test/fiti-deploy/node-configs/<节点名>.env
midr-test/fiti-deploy/node-configs/<节点名>.commands
~~~

nodes-12.csv 记录 SSH 入口、node-id、transport-address、边缘 BGP 标志、角色和群组。env 文件被安装为目标机的 /etc/midr/node.env；commands 文件被安装为 /etc/midr/node.commands。

当前角色约定：

| 角色 | 进程 |
|---|---|
| 边缘节点（edge_bgp=yes、prefix_mode=socket） | zebra、bgpd、midrd、Prefix Provider |
| 内部节点（edge_bgp=no、prefix_mode=none） | zebra、midrd |
| 专职 bootstrap（edge_bgp=no、prefix_mode=none、群号 0） | zebra、midrd |

bootstrap、group-rep 和 member 是 MIDR 协议角色。本实验的 bootstrap 为专职控制面，禁止同时运行边缘 bgpd 和 Provider；初始群代表为北航（Group 1）和复旦（Group 2），武汉和郑州 R1 为自动分群的边缘成员，普通成员可为边缘或内部节点。修改分工时同时更新 nodes-12.csv、inventory-12.csv、env 和 commands，再执行 check/apply。

## 4. 在 90 准备发布包

以下命令在 FITI-90 的 FRR 源码目录执行。示例源码目录是 /home/guest/yhy/frr：

`RELEASE_ID` 由源码提交短哈希和 UTC 构建时间生成，用于唯一标识这次发布。先在当前 90 shell 中执行下面两行：

~~~bash
cd /home/guest/yhy/frr
export RELEASE_ID="$(git rev-parse --short=12 HEAD)-$(date -u +%Y%m%dT%H%M%SZ)"
export RELEASE_DIR="/tmp/midr-$RELEASE_ID"
printf 'RELEASE_ID=%s\nRELEASE_DIR=%s\n' "$RELEASE_ID" "$RELEASE_DIR"
~~~

发布包建好以后，部署命令使用：

~~~bash
export RELEASE_SRC="$RELEASE_DIR"
test -f "$RELEASE_SRC/RELEASE_ID"
test -f "$RELEASE_SRC/SHA256SUMS"
~~~

重新登录 90 后变量不会保留。此时将实际目录名填入 `RELEASE_SRC`，再从包内恢复 `RELEASE_ID`：

~~~bash
export RELEASE_SRC=/tmp/midr-5228cff9b3be-20261001T154159Z
export RELEASE_ID="$(cat "$RELEASE_SRC/RELEASE_ID")"
printf 'RELEASE_SRC=%s\nRELEASE_ID=%s\n' "$RELEASE_SRC" "$RELEASE_ID"
test -f "$RELEASE_SRC/SHA256SUMS"
~~~

~~~bash
cd /home/guest/yhy/frr
git status --short --branch
git rev-parse HEAD
make -j"$(nproc)" midrd/midrd zebra/zebra bgpd/bgpd vtysh/vtysh

rm -rf "$RELEASE_DIR"
install -d -m 755 "$RELEASE_DIR/lib"

cp -L midrd/.libs/midrd "$RELEASE_DIR/midrd"
cp -L zebra/.libs/zebra "$RELEASE_DIR/zebra"
cp -L bgpd/.libs/bgpd "$RELEASE_DIR/bgpd"
# vtysh/vtysh 是 libtool 启动包装器；发布包必须复制实际 ELF。
cp -L vtysh/.libs/vtysh "$RELEASE_DIR/vtysh"
cp -L doc/midr-doc/deployment-tools/midrd-vty.py \
  "$RELEASE_DIR/midrd-vty.py"

cat >"$RELEASE_DIR/run-midrd.sh" <<'EOF'
#!/bin/sh
set -eu
BASE_DIR=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd -P)
export LD_LIBRARY_PATH="$BASE_DIR/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
exec "$BASE_DIR/midrd" "$@"
EOF

chmod 0755 "$RELEASE_DIR"/midrd "$RELEASE_DIR"/zebra \
  "$RELEASE_DIR"/bgpd "$RELEASE_DIR"/vtysh \
  "$RELEASE_DIR"/run-midrd.sh "$RELEASE_DIR"/midrd-vty.py
printf '%s\n' "$RELEASE_ID" >"$RELEASE_DIR/RELEASE_ID"
git rev-parse HEAD >"$RELEASE_DIR/GIT_COMMIT"
(cd "$RELEASE_DIR" && \
  find . -type f ! -name SHA256SUMS ! -name RELEASE_ID ! -name GIT_COMMIT \
    -printf '%P\n' | sort | xargs sha256sum) >"$RELEASE_DIR/SHA256SUMS"
~~~

lib 目录必须包含 ldd 报告中缺失的非系统共享库；发布清单会同时校验这些库。先检查：

~~~bash
for binary in midrd zebra bgpd vtysh; do
  echo "===== $binary ====="
  LD_LIBRARY_PATH="$RELEASE_DIR/lib" ldd "$RELEASE_DIR/$binary"
done
~~~

输出中出现 not found 时不能上传发布包。根据 ldd 中的实际绝对路径把对应非系统库复制到 RELEASE_DIR/lib，再重复 ldd；不能用一个不匹配版本的库临时替代。最后校验：

~~~bash
(cd "$RELEASE_DIR" && sha256sum -c SHA256SUMS)
find "$RELEASE_DIR" -maxdepth 2 -type f -printf '%P\n' | sort
~~~

发布包至少包含 midrd、zebra、bgpd、vtysh、run-midrd.sh、midrd-vty.py、lib/ 和 SHA256SUMS。将完整目录上传到 90 的 /tmp，保留 RELEASE_ID：

~~~bash
scp -r "$RELEASE_DIR" guest@172.20.20.1:/tmp/
~~~

实际 SSH 主机和用户以 FITI 管理入口为准。

## 6. 单节点 check 和 apply

在 90 的 FRR 源码目录执行。RELEASE_SRC 必须指向本次上传的完整目录：

`deploy-node-from-90.sh` 只负责 90 侧编排：读取 `nodes-12.csv` 和 `node-configs/`，校验发布包，创建临时 staging，并通过 SSH/SCP 调用目标机的 `install-node-local.sh`。后者是一次性安装器，不是常驻进程。`check` 不停止服务；`apply` 会先备份，再停止旧 `midrd`、`bgpd`、`zebra` 和系统 `frr.service`，安装本次发布，按 zebra → 边缘 bgpd → midrd 顺序启动，并在失败时恢复备份。

发布目录必须是完整且不可变的版本目录。安装器会在停止任何服务前校验二进制、脚本和 `lib/` 共享库；切换时会等待旧 FRR 和各 daemon 完全退出。如果目标机已经存在同名但不完整的目录，会拒绝切换，避免把缺少共享库的半成品当成正式版本。此时应使用新的 `RELEASE_ID`，或确认没有进程使用后清理残缺目录，再重新执行 `check`。

~~~bash
cd /home/guest/yhy/frr
# 沿用第 4 节已经设置的 RELEASE_SRC；如果重新登录 90，先按前面的恢复示例设置它。
test -f "$RELEASE_SRC/SHA256SUMS"

bash midr-test/fiti-deploy/deploy-node-from-90.sh \
  --node MIDR_fudan --mode check
~~~

check 会校验发布包、共享库、目标机接口、默认网关、FRR 配置和 Netplan，不停止现有服务。check 通过后才执行 apply：

~~~bash
bash midr-test/fiti-deploy/deploy-node-from-90.sh \
  --node MIDR_fudan --mode apply
~~~

apply 在目标机完成以下事务：

1. 备份 /etc/frr、/etc/netplan、/etc/midr、服务状态、旧进程和路由表。
2. 停止旧 midrd、bgpd、zebra 和系统 frr.service。
3. 将发布包复制到 `/opt/midr-releases/midr-${RELEASE_ID}`。
4. 安装 node.env、node.commands、zebra.conf、bgpd.conf 和 systemd 单元。
5. 清理旧的运行时 socket，但不删除 sequence 文件。
6. 按 zebra、bgpd、midrd 顺序启动服务。
7. 等待 ZAPI 和 midrd VTY socket，加载 node.commands。
8. 校验实际运行的可执行文件来自本次发布目录，并写入 /var/lib/midr/last-deploy-backup。

apply 成功后，目标机检查：

~~~bash
systemctl is-active midr-zebra.service midrd.service
systemctl is-active midr-bgpd.service       # 仅 edge_bgp=yes
readlink -f /opt/midr-current
test -S /run/midr/zserv.api
test -S /run/midr/midrd.vty
ss -ltnp | grep ':5871'
~~~

批量上线使用：

~~~bash
# 沿用前面已经设置并校验过的 RELEASE_SRC。
test -f "$RELEASE_SRC/SHA256SUMS"

bash midr-test/fiti-deploy/deploy-batch-from-90.sh \
  --phase bootstrap --mode check
bash midr-test/fiti-deploy/deploy-batch-from-90.sh \
  --phase bootstrap --mode apply
~~~

representatives 和 members 阶段按 03 文档顺序执行。批量脚本默认遇到失败节点即停止；只有查看该节点日志并确认后续操作安全时才使用 --continue。

## 7. systemd 日常操作

以下命令在目标节点执行：

~~~bash
systemctl status midr-zebra.service midr-bgpd.service midrd.service --no-pager
systemctl is-active midr-zebra.service midrd.service

systemctl start midr-zebra.service
systemctl start midr-bgpd.service       # 仅边缘节点
systemctl start midrd.service

systemctl stop midrd.service
systemctl stop midr-bgpd.service       # 仅边缘节点
systemctl stop midr-zebra.service

systemctl restart midrd.service
systemctl restart midr-bgpd.service    # 仅边缘节点
systemctl restart midr-zebra.service
~~~

推荐的服务顺序是先启动 zebra，再启动边缘 bgpd，最后启动 midrd；停止时反向执行。systemctl restart midr-zebra.service 会短暂中断依赖它的 midrd，只有需要重启匹配 Zebra 或修复 Zebra 状态时才执行。单纯修改 MIDR VTY 配置只需重启 midrd。

确认服务是否开机启动：

~~~bash
systemctl is-enabled midr-zebra.service midrd.service
systemctl is-enabled midr-bgpd.service       # 仅边缘节点
~~~

服务文件已经通过 WantedBy=multi-user.target 安装。内部节点应保持 midr-bgpd.service disabled、inactive。

## 8. 配置修改和重载

编辑持久配置：

~~~bash
cp -a /etc/midr/node.commands \
  "/var/lib/midr/node.commands.$(date -u +%Y%m%dT%H%M%SZ).bak"
vi /etc/midr/node.commands
chmod 0600 /etc/midr/node.commands
systemctl restart midrd.service
~~~

重启后由 midrd.service 的 ExecStartPost 自动执行：

~~~bash
python3 /opt/midr-current/midrd-vty.py \
  --socket /run/midr/midrd.vty \
  --commands-file /etc/midr/node.commands
~~~

node.commands 是文本形式的持久 VTY 命令，例如 transport-address、role、group-id、bootstrap 和固定 bootstrap session。/run/midr/midrd.vty 是服务启动后创建的运行时 socket；它既不会替代 node.commands，也不需要保存。

手工查询不修改配置：

~~~bash
python3 /opt/midr-current/midrd-vty.py \
  --socket /run/midr/midrd.vty \
  -c 'show midr self' \
  -c 'show midr neighbors' \
  -c 'show midr nodes' \
  -c 'show midr links' \
  -c 'show midr spf' \
  -c 'show midr virtual-links'
~~~

如需查询 Zebra 或 bgpd：

~~~bash
export LD_LIBRARY_PATH="$(readlink -f /opt/midr-current)/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
/opt/midr-current/vtysh --vty_socket /run/midr -d zebra -c 'show ip route'
/opt/midr-current/vtysh --vty_socket /run/midr -d bgpd -c 'show bgp summary'
~~~

vtysh 不需要单独启动；它连接已经运行的 daemon。

## 9. 常用状态和日志

~~~bash
journalctl -u midr-zebra.service -n 100 --no-pager
journalctl -u midr-bgpd.service -n 100 --no-pager
journalctl -u midrd.service -n 100 --no-pager
tail -n 100 /var/log/midr/*-midrd.log
tail -n 100 /var/log/midr/*-zebra.log
tail -n 100 /var/log/midr/*-bgpd.log

pgrep -af 'midrd|zebra|bgpd'
ss -ltnp | grep ':5871' || true
ss -xl | grep '/run/midr' || true
ip -6 route show default
ip -6 route show proto 199
ip -4 route show proto 199
~~~

按故障层次排查：

| 现象 | 首先检查 |
|---|---|
| midrd initialization failed | midr-zebra.service、/run/midr/zserv.api、发布包 ldd 和 journalctl |
| VTY socket 不存在 | midrd.service 状态和日志 |
| Session 为 Connect | ip -6 route get 对端 locator、TCP 5871、防火墙和两端日志 |
| Link 不为 up | Session、Node directory、Link 日志和 underlay RTT/loss |
| GRE READY 但业务不通 | ip route show proto 199、route get、业务 Prefix 和返回路径 |
| 内部节点出现 bgpd | 停止并禁用 midr-bgpd.service，确认旧系统 frr.service 未重新拉起 bgpd |
| 服务启动了旧二进制 | systemctl show -p MainPID、readlink -f /proc/<pid>/exe、readlink -f /opt/midr-current |

FRR 配置异常时使用 systemctl restart frr 清理系统 FRR 的陈旧状态；不能让 frr.service 与本实验的 zebra 同时管理同一个 FIB。目标 MIDR 主机切换完成后，frr.service 应保持 disabled/inactive。

## 10. 升级

每个版本都使用新的发布目录，不能覆盖旧目录：

~~~bash
# 先按第 4 节设置本次新发布包的 RELEASE_SRC；下面沿用该变量。
test -f "$RELEASE_SRC/SHA256SUMS"
bash midr-test/fiti-deploy/deploy-node-from-90.sh \
  --node MIDR_fudan --mode check
bash midr-test/fiti-deploy/deploy-node-from-90.sh \
  --node MIDR_fudan --mode apply
~~~

升级过程保留：

~~~text
/opt/midr-releases/midr-<old-release-id>
/etc/midr/node.env
/etc/midr/node.commands
/var/lib/midr/<node-id>.seq
~~~

升级必须同时替换 midrd、zebra、bgpd、vtysh 和 lib；不能只上传一个 midrd。成功后以 systemctl、可执行文件路径、Session、Link、SPF、proto 199 和业务流量重新验收。

## 11. 回滚

安装器失败时会尝试自动恢复最近一次备份。查看备份：

~~~bash
ls -1dt /var/lib/midr/deploy-backups/* | head
cat /var/lib/midr/last-deploy-backup
~~~

人工回滚应使用与目标配置匹配的旧完整发布包，再通过同一 deploy-node-from-90.sh 执行 apply；不能把旧 midrd 单独覆盖到新 zebra 上。回滚后按 zebra、bgpd（边缘）、midrd 顺序确认服务，并重新加载原有 node.commands。

## 12. 常用参数说明

| 参数或变量 | 作用 |
|---|---|
| MIDR_NODE_ID | 稳定的数字身份，必须与序列文件和节点清单一致 |
| MIDR_LOCATOR | 本节点 transport-address，必须已配置在目标接口 |
| MIDR_GATEWAY | 本站 BGP-R 的下一跳地址，用于 underlay 默认路由门禁 |
| MIDR_RELEASE_DIR | 当前完整发布目录，由安装器写入 node.env |
| MIDR_EDGE_BGP | yes 启动 bgpd，no 禁用 bgpd |
| MIDR_PREFIX_MODE | none 不连接 Prefix Provider；socket 使用 prefix socket |
| --zserv-path | midrd 连接 Zebra 的 ZAPI socket |
| --vty_socket | VTY socket 所在目录 |
| --sequence-file | MIDR sequence 持久文件 |
| --pidfile | midrd 运行时 PID 文件 |
| --takeover-delay | 会话接管等待时间 |
| --lifetime | 节点对象存活时间 |
| --hold-time | Session 保持时间 |
| --prefix-socket | 仅在 MIDR_PREFIX_MODE=socket 且 socket 存在时传入 |

--no-zebra、--peer、--link 和 --link-addr 是早期两节点调试参数，不属于正式 systemd 服务。正式部署不手工创建 mgre-* 接口，GRE 由 midrd 根据控制面状态自动创建。
