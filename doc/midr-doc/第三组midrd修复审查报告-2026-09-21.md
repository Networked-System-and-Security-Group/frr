### 检查 2 — `lib/log.c command_types[]`

- `DESC_ENTRY(T)` 宏：`lib/log.c:320` `#define DESC_ENTRY(T) [(T)] = { (T), (#T), '\0' }`

- 越界保护：`lib/log.c:511` `if (command >= array_size(command_types))` + `:516 return command_types[command].string`。
  `array_size == 最大指定下标 + 1 == 149`（最大下标 `ZEBRA_GRE_DELETE == 148`，且该 `DESC_ENTRY` 已存在），

- 自述文档是否夸大？**否。** `e7c78d33a7` 提交信息明确写"`command_types[]` is built with designated
  initialisers ... so its lookup is order-independent; the two DESC_ENTRY lines are nevertheless moved
  ... to keep the source order readable and to satisfy the new gate."——表述与事实一致。

**判定：PASS。** 重排功能上装饰性，且被测方未夸大。

### 2.2 deferred FIB 失败后 desired/installed 一致性 — **PASS**
实现（`midrd/midr-dp-backend.c`）：
- `dp_flush_timer_cb()`（`:749-771`）在异步 flush 失败时调用 `dp_retain_remainder()`（`:668-677`，把队列余量
  标记 `recovery=true`）而**不再丢弃**，并 `dp_schedule_recovery()`。
- `dp_abort_pending_ops()`（`:686-702`）只丢弃**非 recovery**的当前轮操作；保留批次穿越后续 round 的 abort。
- `dp_recovery_cb()`（`:787-857`）先重发保留批次，成功后再 `midr_spf_install_resync()`。
- `dp_process_one_op()`（`:566-626`）在 `dp_installed_set()` 失败时**保持操作在队列**且不伪装已安装。
与审查 2.2 的"保留失败批次并触发完整 replay/resync"选项 (b) 一致。
边界诚实说明：`midr_spf_install_resync()` 在 `desired` 代未变时**短路为 no-op**（`midr-spf-install.c:391-396`），
所以真正重建缺失安装的是"保留批次本身"，resync 只是规格可见的对账。该语义在文件头与提交信息中已如实写明。
覆盖交错（`midrd/dp-backend-test.c`，均断言可观测状态而非仅返回码）：
`test_deferred_partial_batch_failure`（:625）、`test_deferred_whole_batch_failure`（:673，含
`midr_zebra_route_abort()` 后保留批次仍在 :697-700）、`test_deferred_failure_across_reconnect`（:722）、
`test_recovery_with_new_desired_inflight`（:773）。

### 2.3 恢复重试不能因达到上限而永久停滞 — **PASS**
`dp_recovery_cb()` 全状态机逐出口核查（`midrd/midr-dp-backend.c:787-857`）：
- 无 ctx → `IDLE` 且无 pending 需要恢复（backend 已不可用），无搁置；
- zebra 不可达 → `STALLED` + **必定** `dp_recovery_arm(HEARTBEAT_MS=2000)`（:801-805）；
- 批次仍失败 → 未到上限 `ACTIVE`+100ms（:816-821），到上限 `STALLED`+2000ms（:825-830）；
- resync 仍失败 → 未到上限 `ACTIVE`+100ms，到上限 `STALLED`+2000ms（:840-850）；
- 否则 `IDLE` + 清零（:852-856）。
**不存在"到上限后无定时器 armed"的出口**：`STALLED` 下回调每 2s 自重臂，形成慢心跳重试直至成功/重连/新代。
`dp_recovery_kick()`（:865-874）由"新 desired 更新"（`dp_route_update_deferred` :992）与
"zebra 重连"（`dp_zebra_connected` :910）触发，取消并前置定时器、重置预算。
`dp_backend_destroy()`（:1045-1064）取消 `t_deferred`/`t_recovery` 并置 `IDLE`。
测试 `test_recovery_past_cap_rearm`（:829）断言 `recovery_stalled && recovery_attempts>=50 &&
installed==1 && pending==2`，随后在**无重连**下由新 desired 重新触发并收敛——日志 `send-failures=51`、
`retained batch still failing after 50 retries (-5), slow heartbeat armed` 与之一致。

`midrd/midr-dp-backend.c:253-303`：先 `calloc` 整个 entry，再 `dp_paths_dup`（失败即 `free(e)` 返回 `-ENOMEM`），

### 3.2 backend ops 生命周期 — **PASS**

### 3.4 同名接口绑定新端点时同步更新 registry — **PASS**

### D5（低严重度未防护路径）`midr_dp_backend_start()` 忽略 `dp_flush_pending()` 返回值
`midrd/midr-dp-backend.c:1113-1116`：
```c
if (b->zc->sock >= 0 && listcount(b->pending_ops)) {
        b->immediate_next = false;
        (void)dp_flush_pending(b);      /* 失败：批次留在队列，但无人安排 recovery */
}
```
若此处 flush 失败，操作留在队列而 `recovery_state` 仍为 `IDLE`、无定时器 armed（不像
`dp_flush_timer_cb` 会 `dp_retain_remainder()+dp_schedule_recovery()`）。本审查**未能构造可达的交错**
（`register()` 路径已通过 `immediate_next` 触发过 flush，失败会走 adapter abort 清空当前轮），
故严重度低；但它是一条"失败即静默遗留在队列"的无防护出口，建议把返回值并入 `dp_schedule_recovery()` 分支。

### D6（提示，非缺陷）`dp_installed_set()` 的"原地替换"分支生产不可达
`midrd/midr-dp-backend.c:290-301` 的 `existing != e` 分支要求 `hash_get` 命中已存在键，但同一
(prefix, instance) 已先经 `dp_installed_lookup()`（`hash_key`/`hash_cmp` 完全相同）判定为 NULL
（:575/:611），故该分支在生产与测试中都不可达。提交信息对其"旧 payload 不早释"的描述**事实上正确**
（`free(existing->paths)` 确实发生在新 payload 全部就绪之后），但该性质**按构造即不可观测**。
建议：删除该死代码，或用直接单测（绕过 lookup）真正覆盖。
